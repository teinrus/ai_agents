# Runtime агентов

Один автомат на любую роль. Отдельного цикла для домена нет.

## Кто чем владеет

Оркестратор — не LLM-агент. Он принимает задачу, выбирает роль, связывает скиллы, переводит состояния, ставит прогон на паузу, отдаёт порцию в evaluation и возвращает результат только после оценки.

Агент не регистрирует себя, не завершает прогон и не выбирает модель по имени.

Экземпляр сотрудника переживает задачу. `Completed` и `Failed` возвращают роль в `Idle`. Удаляется не сотрудник, а прогон.

## Состояния

`Registered` → `Idle` → `Assigned` → `Running`.

Из `Running`: `WaitingTool`, `WaitingModel`, `WaitingConfirmation`, `Evaluating`, `Failed`.

`WaitingTool` и `WaitingModel` — ожидание внешнего вызова, не отдельные агенты.

`WaitingConfirmation` — политика вернула `confirm`. Обхода шлюза нет. Дальше только одноразовое подтверждение или отказ.

`Evaluating` принадлежит контуру оценки. Из него: обратно в `Running` (есть правка), `Completed` или `Failed`.

`Idle` → `Retired`, когда роль выключена в конфигурации. Журнал прошлых прогонов остаётся.

## Вход прогона

Общие поля: цель, ограничения, необязательный payload, `correlation_id`. Платформа генерирует `run_id`; к нему привязаны лента, раздел `run` и подтверждения. Доменный payload не превращается в тип ядра.

Выбор роли: максимальный `score` не ниже порога — событие `agent.selected`. Порог не взят — остановка без вызова модели, `task.finished` со статусом `no_role`.

Скиллы доступны только из привязки выбранной роли. Событие `skill.bound`.

## Как добавлять поведение

Новый шаг домена — скилл и инструмент роли, не новое состояние автомата.

Новое состояние допустимо только если оно нужно всем ролям. Тогда же обновляются спека, событие `agent.state_changed` и тесты переходов.

## Готово, когда

- Любая роль проходит те же переходы.
- Сотрудник снова в `Idle` после конца прогона.
- Подтверждение нельзя обойти вторым вызовом инструмента.
- В модулях runtime и orchestrator нет доменных импортов.
