# Model router

Роутер стоит над провайдерами. Агент формулирует требования шага. Роутер выбирает модель.

## Требования шага

На каждый шаг, не на весь отдел: способности `coding | reasoning | tools`, предпочтения `cheap | fast | long_context`, нижняя граница окна, метка `purpose` для шины.

Комбинация моделей в одном прогоне — несколько вызовов роутера с разными требованиями. Агент оба `model_id` не знает и не хранит.

## Каталог

Запись: `model_id`, `provider_id`, имя у провайдера, способности, окно, `cost_tier`, `latency_tier`, `enabled`.

Сейчас каталог читается из конфигурации на старте. Позже тот же `list()` читает живой источник. Смена состава — не правка агента.

## Выбор

1. Оставить включённые модели, которые закрывают способности и окно.
2. Упорядочить по предпочтению: `cheap` по `cost_tier`, `fast` по `latency_tier`, `long_context` по окну.
3. При равенстве сохранить порядок каталога.
4. Взять первую и вызвать её провайдера.
5. Пустой список — `NoModelError`. Случайную или «дефолтную» модель не подставлять.

Событие `model.routed`: требования и отклонённые кандидаты. Затем `model.called`.

## Как менять модели

Сейчас — правка конфигурации каталога и перезапуск. Позже — смена источника `list()` без смены сигнатуры. Динамическая смена не требует новой ветки в роли.

Не хардкодить соответствие «почта → модель» ни в роутере, ни в роли.

## Готово, когда

- Два шага с разными требованиями получают разные модели, если каталог это позволяет.
- Выключенная модель не выбирается.
- Пустой список кандидатов виден как ошибка маршрута, не как удачный ответ.
