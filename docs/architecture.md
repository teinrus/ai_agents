# Архитектура AI Department

Контракты платформы цифровых сотрудников. Документ — источник правды для кода. Поведение, которого здесь нет, в код не попадает: сначала правка этого файла, потом реализация.

Методология разработки живёт в `.cursor/`. Инструкции конкретных ролей живут в плагинах ролей. Здесь — только то, что строим.

## 1. Назначение

Платформа исполняет задачи силами набора ролей через один общий цикл: выбор роли, работа агента с моделью и инструментами, обязательная оценка результата, лента событий. Роль входит в платформу конфигурацией и плагином. Ядро ни одной роли не знает.

Клиент общается с платформой через одно окно — приёмную (раздел 19). Приёмная превращает сообщение человека в задачу, передаёт её оркестратору и возвращает ответ по итогам прогона. Оркестратор по-прежнему не LLM: смысл текста разбирает отдельный шаг приёмной, а не он.

Почтовый сотрудник — первая демонстрационная роль. Ядро не содержит типов письма, ящика, IMAP и SMTP. Вторая демонстрационная роль — учёт записей (`records`): чтение списка и черновик записи, без почтового домена.

## 2. Глоссарий

| Термин | Идентификатор | Смысл |
| --- | --- | --- |
| Роль | `role` | Плагин: тип сотрудника. Задаёт `score`, скиллы, потолок риска, обработчики инструментов, схему выхода. |
| Сотрудник | `employee` | Зарегистрированный экземпляр роли с состоянием автомата. Переживает задачи. |
| Задача | `task` | Вход от клиента: цель, ограничения, payload, `correlation_id`. |
| Прогон | `run` | Одно исполнение задачи одним сотрудником. Имеет `run_id`, статус и ленту. |
| Шаг | `step` | Один вызов модели или инструмента внутри прогона. |
| Скилл роли | `skill` | Подключаемая способность роли: инструкция, инструменты, типовые требования к модели. |
| Инструмент | `tool` | Зарегистрированный обработчик с именем, схемой аргументов и уровнем риска. |
| Порт | `port` | Интерфейс ядра, реализация которого подменяема. |
| Адаптер | `adapter` | Реализация порта. |
| Корень сборки | `composition root` | Единственное место, где выбираются адаптеры и читается окружение. |
| Тред | `thread` | Диалог клиента с платформой: сообщения и связанные прогоны. Имеет `thread_id`. |
| Приёмная | `reception` | Шаг платформы, который разбирает сообщение треда и либо отвечает, либо отдаёт задачу оркестратору. |

Автомат принадлежит сотруднику, статус — прогону. Фраза «роль в `Idle`» означает «сотрудник этой роли в `Idle`».

## 3. Границы модулей

Пакеты ядра: `domain`, `orchestrator`, `runtime`, `evaluation`, `memory`, `tools`, `llm`, `events`, `observability`, `dialog`, `api`. Плагины ролей — отдельные пакеты в `roles/<role_id>/`.

| Пакет | Владеет | Не делает |
| --- | --- | --- |
| `domain` | Типы задачи, прогона, состояний, статусов, уровней риска, требований к модели, конверта события; контракт плагина роли | Не зависит ни от одного пакета платформы |
| `orchestrator` | Реестр ролей, приём задачи, выбор роли, привязка скиллов, переводы состояний, передача в evaluation, выдача результата | Не вызывает модель и инструменты; плагины получает из корня сборки |
| `runtime` | Общий цикл шагов агента, обращение к портам | Не ветвится по роли, не знает домен |
| `evaluation` | Порт `Evaluator`, детерминированный оценщик, цикл правок | Не вызывает инструменты, не выбирает модель |
| `memory` | Порт `MemoryBackend`, разделы, изоляция | Не знает домен роли |
| `tools` | Реестр описаний, шлюз, политика риска, одноразовые подтверждения | Не импортирует обработчики ролей; получает уже зарегистрированные |
| `llm` | Каталог моделей, роутер, порт `LlmProvider`, адаптеры | Не знает роль и назначение задачи |
| `events` | Конверт, шина, публикация | Не знает подписчиков |
| `observability` | Подписчики: stdout, счётчики, лента прогона, лента треда | Не влияет на решения |
| `dialog` | Треды, приёмная: разбор сообщения через роутер, передача задачи оркестратору, детерминированный ответ по снимку прогона | Не вызывает инструменты, не выбирает роль вместо оркестратора, не завершает прогон, домен роли не знает |
| `api` | Тонкий HTTP-край | Не содержит правил риска, выбора модели и оценки |
| `roles/<role_id>/` | Плагин: `score`, скиллы, потолок, обработчики, схема выхода | Не импортируется ядром; не вызывает модель и обработчики напрямую |

Направление зависимостей: `domain` ← порты ← `runtime` / `orchestrator` ← `dialog` ← `api`. Плагин роли зависит только от `domain`. Ядро плагин не импортирует: реестр в `orchestrator` получает плагины из корня сборки.

Платформенная правка меняет контракт, которым пользуются все роли: состояние, событие, раздел памяти, уровень риска, требования к модели, статус прогона. Правка роли меняет `score`, скиллы, потолок, обработчики, схему выхода. Если новой роли потребовалась правка `orchestrator` или `runtime`, контракт платформы неверен.

## 4. Контракт роли

Плагин роли предоставляет:

- `role_id` — стабильный идентификатор.
- `description` — одно-два предложения о том, какие задачи роль берёт. Читает приёмная при разборе сообщения. Имена инструментов и модели сюда не входят.
- `score(task) -> float` в диапазоне `[0, 1]`. Чистая функция от задачи. Модель не вызывает. Роль, участвующая в диалоге, возвращает не ниже `role_threshold`, когда `payload.channel` равен её `role_id` (раздел 19.2).
- `skills` — список скиллов роли. Каждый: `skill_id`, инструкция шага, имена инструментов, типовые требования к модели.
- `risk_ceiling` — потолок риска роли. Не выше платформенного.
- `tools` — описания инструментов с обработчиками (раздел 8).
- `output_schema` — JSON-схема итогового выхода прогона. Используется evaluation.
- `view` — необязательное представление доменных полей payload для панели. Этап 3.

Роль не может: вызывать модель напрямую, вызывать обработчик инструмента в обход шлюза, читать чужой раздел `run`, поднимать потолок риска, завершать прогон, выбирать модель по имени, оценивать саму себя.

Включение и выключение роли — конфигурация корня сборки. Выключение переводит сотрудников роли из `Idle` в `Retired`; ленты прошлых прогонов сохраняются.

## 5. Вход прогона

Задача:

- `goal` — текст цели.
- `constraints` — `max_steps`, `max_revisions`, необязательный `deadline`. Отсутствующие берутся из платформенных дефолтов. Значение выше платформенного максимума — ошибка валидации на входе, не молчаливое урезание.
- `payload` — непрозрачный объект. Ядро его не типизирует и не читает. Доступен `score` роли и скиллам.
- `correlation_id` — внешняя сквозная метка. Если клиент не прислал, платформа генерирует. Для изоляции и безопасности не используется.

Платформа генерирует `run_id`. К нему привязаны раздел памяти `run`, подтверждения инструментов и лента.

Платформенные дефолты и максимумы задаются конфигурацией корня сборки: `max_steps` (дефолт 20, максимум 100), `max_revisions` (дефолт 1, максимум 3), порог выбора роли `role_threshold` (дефолт 0.5), потолок риска платформы `platform_risk_ceiling` (дефолт `act`).

## 6. Автомат сотрудника

Состояния: `Registered`, `Idle`, `Assigned`, `Running`, `WaitingTool`, `WaitingModel`, `WaitingConfirmation`, `Evaluating`, `Completed`, `Failed`, `Retired`.

| Из | В | Когда |
| --- | --- | --- |
| `Registered` | `Idle` | Реестр принял плагин, сотрудник создан |
| `Idle` | `Assigned` | Оркестратор выбрал этого сотрудника для задачи |
| `Assigned` | `Running` | Скиллы привязаны, прогон начат |
| `Running` | `WaitingModel` | Runtime отправил запрос в роутер |
| `WaitingModel` | `Running` | Ответ модели получен |
| `WaitingModel` | `Failed` | `NoModelError` или ошибка провайдера после исчерпания повторов |
| `Running` | `WaitingTool` | Политика вернула `allow`, обработчик вызван |
| `WaitingTool` | `Running` | Обработчик вернул результат или ошибку; ошибка публикуется как `tool.failed` и передаётся агенту результатом шага, прогон не падает |
| `Running` | `WaitingConfirmation` | Политика вернула `confirm` |
| `WaitingConfirmation` | `Running` | Клиент подтвердил: инструмент выполнен, результат передан агенту. Клиент отказал: инструмент не выполнен, агенту передан результат `denied` |
| `WaitingConfirmation` | `Failed` | Истёк `deadline` задачи |
| `Running` | `Evaluating` | Агент сформировал итог или достигнут `max_steps` |
| `Running` | `Failed` | Внутренняя ошибка runtime |
| `Evaluating` | `Running` | `rejected`, правки не исчерпаны |
| `Evaluating` | `Completed` | `passed` |
| `Evaluating` | `Failed` | `rejected`, правки исчерпаны; статус прогона `rejected` |
| `Completed` | `Idle` | Автоматически, тот же такт |
| `Failed` | `Idle` | Автоматически, тот же такт |
| `Idle` | `Retired` | Роль выключена в конфигурации |

Инварианты:

- `Completed` достижим только из `Evaluating`. Другого пути нет.
- Из `WaitingConfirmation` выход только через подтверждение, отказ или `deadline`. Второй вызов инструмента, другой скилл или ответ модели это состояние не покидают.
- `Completed` и `Failed` терминальны для прогона и переходны для сотрудника: он возвращается в `Idle` и готов к следующей задаче. Сотрудник не удаляется.
- `WaitingTool` и `WaitingModel` — ожидания внутри одного сотрудника, не отдельные агенты.
- `deny` политики не меняет состояние: агент получает результат `denied` и остаётся в `Running`.

Каждый переход публикует `agent.state_changed`. Новое состояние допустимо только если нужно всем ролям; тогда правится этот раздел, событие и тесты переходов.

## 7. Статусы прогона

| Статус | Когда | Состояние сотрудника |
| --- | --- | --- |
| `completed` | Evaluation вернула `passed` | `Completed` → `Idle` |
| `rejected` | Evaluation вернула `rejected`, правки исчерпаны | `Failed` → `Idle` |
| `failed` | Ошибка модели, провайдера, runtime или `deadline` | `Failed` → `Idle` |
| `no_role` | Ни одна роль не взяла порог | Сотрудник не назначался |

У `no_role` есть уточнение `failure_reason = busy`: роль взяла бы порог, но её сотрудник не в `Idle` — занят другим прогоном или ждёт подтверждения. Клиенту это отличимо от «такой работы никто не делает».

`task.finished` публикуется при любом статусе и несёт его. Статус `completed` без предшествующего `evaluation.completed` с вердиктом `passed` в той же ленте — дефект.

## 8. Выбор роли и скиллов

1. Оркестратор вызывает `score(task)` у каждой включённой роли. Модель не вызывается.
2. Берётся максимальный `score` не ниже `role_threshold`. При равенстве — порядок реестра.
3. Нет кандидата — прогон завершается со статусом `no_role`, событие `task.finished`. Модель и инструменты не вызывались.
4. Выбор публикуется событием `agent.selected`: `role_id`, `score`, отклонённые кандидаты со своими `score`.
5. Привязываются только скиллы выбранной роли. Событие `skill.bound` на список. Инструменты вне этих скиллов для прогона не существуют: шлюз отвечает `deny`.

## 9. Модель

### 9.1. Требования шага

Агент задаёт на каждый шаг, не на прогон:

- `capabilities` — подмножество `{coding, reasoning, tools}`. Обязательно непусто.
- `preferences` — упорядоченный список из `{cheap, fast, long_context}`. Порядок — приоритет сортировки.
- `min_context_window` — нижняя граница окна в токенах.
- `purpose` — короткая метка для шины.

Имя модели, `model_id` и провайдер агенту неизвестны и в памяти не хранятся.

### 9.2. Каталог

Запись: `model_id`, `provider_id`, `provider_model_name`, `capabilities`, `context_window`, `cost_tier`, `latency_tier`, `enabled`.

Порт каталога: `ModelCatalog.list() -> list[entry]`. Первая реализация читает конфигурацию на старте. Живой источник перечитывает тот же JSON при каждом `list()` и включается конфигурацией. Сигнатура прежняя.

Соответствие «роль → модель» в каталоге, роутере и роли не задаётся.

### 9.3. Роутер

1. Оставить записи с `enabled = true`, покрывающие все `capabilities` и `context_window >= min_context_window`.
2. Отсортировать лексикографически по `preferences`: `cheap` → `cost_tier` по возрастанию, `fast` → `latency_tier` по возрастанию, `long_context` → `context_window` по убыванию.
3. При равенстве сохранить порядок каталога.
4. Пустой список — `NoModelError`. Дефолтная или случайная модель не подставляется.
5. Публиковать `model.routed`: требования, выбранная запись, отклонённые кандидаты с причиной.
6. Вызвать провайдера выбранной записи. Публиковать `model.called`.

### 9.4. Провайдер

Порт: `LlmProvider.complete(provider_model_name, request) -> response`. Запрос: сообщения, доступные описания инструментов, параметры. Единственный параметр генерации — `temperature` (необязательный, `0..2`): пустое значение оставляет умолчание провайдера, `0` просят шаги-классификаторы вроде приёмной, где нужен повторяемый выбор. Ответ: текст и список запрошенных tool-calls. Типы SDK наружу не выходят.

Провайдер не читает требования, не ранжирует и не публикует маршрут.

Сбой — `ProviderError` с `kind` из `{timeout, rate_limit, unavailable, invalid_response, auth}` и коротким сообщением. Для `timeout`, `rate_limit`, `unavailable` runtime повторяет вызов той же модели не более `max_provider_retries` раз (дефолт 1). Каждая неудачная попытка публикует `model.failed`. Модель молча не подменяется. После исчерпания повторов прогон получает статус `failed`.

Адаптеры: `MockLlmProvider` с заданными ответами, один адаптер к OpenAI-совместимому локальному endpoint и один облачный адаптер того же протокола с отдельным `provider_id`. Это не набор вендоров. Ключ и базовый URL адаптер получает из окружения в корне сборки.

## 10. Инструменты

### 10.1. Описание

`name`, JSON-схема аргументов, `risk_level`, обработчик. Уровни по возрастанию: `read` < `draft` < `act` < `destructive`.

Обработчик живёт в плагине роли или общем адаптере. Регистрируется в реестре инструментов на старте. Шлюз получает обработчик из реестра и домен не импортирует.

Перед политикой шлюз проверяет аргументы вызова по JSON-схеме инструмента. Несоответствие — `tool.failed` с `kind = arguments` и текстом первой ошибки (для `pattern` вместо регулярного выражения берётся `description` поля, если оно задано); результат шага уходит модели, подтверждение не открывается, обработчик не вызывается. Так человека не просят разрешить действие с заведомо негодными данными — пустым адресом, числом в строке, заглушкой вместо значения. Схема — единственный общий язык ограничений: роль описывает в ней формат (`pattern`, `minLength`, `enum`), ядро эти форматы не знает.

### 10.2. Политика

Чистая функция `decide(call, context) -> allow | confirm | deny`, где `context` — `run_id`, `role_id`, список инструментов привязанных скиллов, потолок роли, потолок платформы, активные подтверждения прогона.

Правила применяются по порядку, первое совпавшее решает:

1. Инструмент не входит в привязанные скиллы — `deny`.
2. `risk_level` выше потолка роли или потолка платформы — `deny`.
3. `risk_level = destructive` — `deny`. Платформенный потолок по умолчанию `act`; открытие `destructive` — отдельное платформенное решение вне текущего плана.
4. `read`, `draft` — `allow`.
5. `act` — `allow`, если есть неиспользованное подтверждение на `run_id` и хеш существенных аргументов; подтверждение гасится. Иначе — `confirm`.

Промпт, скилл, модель и payload потолок не поднимают. Роль может только сузить.

Ошибка политики — `deny`, не исключение. Пути вызова обработчика в обход `decide` в коде нет, включая отладочный.

### 10.3. Подтверждение

При `confirm` платформа создаёт запись ожидания: `confirmation_id`, `run_id`, `tool`, `args_hash`, `expires_at`. Публикуется `tool.confirmation_required` с `confirmation_id`, именем инструмента и безопасными аргументами.

Клиент отвечает на `confirmation_id`: `approve` или `reject`. Подтверждение одноразовое и действует только для этого `run_id` и этого `args_hash`. Повтор того же `act` с другими аргументами или в другом прогоне снова требует `confirm`.

Хеш существенных аргументов: канонический JSON аргументов без полей, помеченных в схеме инструмента как несущественные. Секреты в аргументы не входят: учётные данные обработчик берёт из окружения.

События: `tool.invoked` на успешный вызов, `tool.denied` на `deny`, `tool.confirmation_required` на `confirm`.

## 11. Evaluation

Отдельный контур. Запускается, когда runtime перевёл прогон в `Evaluating`. Вход: задача, итоговый выход, трасса шагов, `role_id`, потолок роли.

Порт: `Evaluator.evaluate(task, output, trace) -> verdict`, где `verdict` — `passed | rejected` и список проверок с результатом и структурированным замечанием.

Цикл:

1. `evaluation.started`.
2. `Evaluator.evaluate`.
3. `evaluation.completed` с вердиктом и проверками — при любом исходе.
4. `passed` — состояние `Completed`, статус `completed`.
5. `rejected`, правок меньше `max_revisions` — `evaluation.revision_requested` с замечаниями, сотрудник в `Running`. Правка идёт через те же шлюзы модели и инструментов.
6. `rejected`, правки исчерпаны — состояние `Failed`, статус `rejected`.

Детерминированный оценщик этапа реализации проверяет без домена:

- выход соответствует `output_schema` роли;
- число шагов не превысило `max_steps`;
- в трассе нет `act` без предшествующего погашенного подтверждения;
- в трассе нет вызова выше потолка роли;
- `role_id` трассы совпадает с выбранной ролью;
- `tool_evidence`: если прогону привязан хотя бы один инструмент, в трассе есть хотя бы одна попытка вызова — исполненная, отклонённая человеком, запрещённая политикой или отвергнутая схемой. Итог сотрудника, у которого есть инструменты, но который ни разу к ним не обратился, — рассказ без дела: «письмо отправлено» без отправки. Такой итог уходит на правку с замечанием выполнить задачу инструментами; роль без инструментов проверку проходит.

Трасса для оценщика несёт `bound_tools` — имена инструментов привязанных скиллов — и все попытки вызова: у исполненных `invoked = true`, у отклонённых, запрещённых и отвергнутых схемой — `invoked = false`.

Второй оценщик качества реализует тот же порт. Тесты используют mock-оценщик с заданным вердиктом. Оценщик не вызывает инструменты и не выбирает модель; если ему нужна модель, он заявляет требования роутеру как любой шаг.

## 12. Память

Порт `MemoryBackend`: `put(section, key, value)`, `get(section, key)`, `search(section, query) -> list[record]`, `list(section, prefix) -> list[key]`.

Область раздела runtime подставляет сам из контекста прогона; агент идентификаторы не передаёт и чужой раздел адресовать не может.

| Раздел | Область | Чтение | Запись |
| --- | --- | --- | --- |
| `run` | `run_id` | Только этот прогон | Только этот прогон |
| `agent` | `role_id` | Все прогоны этой роли | Все прогоны этой роли |
| `department` | платформа | Все роли | Все роли |

`search` в первой реализации — поиск подстроки по ключу и текстовому представлению значения. Другой backend может искать лучше, но обязан вернуть не меньше.

В память пишется итог решения. Не пишутся: сырые внешние документы, секреты, токены подтверждения, содержимое, запрещённое на INFO в шине.

Реализации: `MockMemory` для тестов, `InMemory` для локального запуска, SQLite как первое сохраняемое хранилище, распределённое хранилище — общий каталог файлов, который открывают несколько процессов. Смена backend не меняет код роли и сигнатуры порта. Новый раздел — регистрация в платформе, не ветка агента.

## 13. Шина событий

### 13.1. Конверт

| Поле | Значение |
| --- | --- |
| `ts` | UTC, ISO-8601 |
| `seq` | Номер события в прогоне, строго возрастает с 1 |
| `level` | `DEBUG | INFO | WARNING | ERROR` |
| `correlation_id` | Внешняя метка задачи |
| `run_id` | Идентификатор прогона; пусто у `task.received` до создания прогона и у событий треда, включая маршрут и вызов модели шага приёмной. У событий треда ключ — `correlation_id`, равный `thread_id` |
| `event` | Имя из списка ниже |
| `role_id` | Необязательно |
| `step` | Необязательно, номер шага |
| `message` | Короткий текст |
| `payload` | Безопасные поля решения |

`seq` даёт порядок независимо от транспорта. Подписчик, получающий события из внешнего брокера, восстанавливает порядок по `run_id` и `seq`.

### 13.2. События

| Событие | Уровень | Payload |
| --- | --- | --- |
| `task.received` | INFO | `goal`, `constraints`, `payload` клиента |
| `agent.selected` | INFO | `role_id`, `score`, отклонённые кандидаты |
| `agent.state_changed` | INFO | `from`, `to`, причина |
| `skill.bound` | INFO | список `skill_id` |
| `model.routed` | INFO | требования, `model_id`, отклонённые кандидаты с причиной |
| `model.called` | INFO | `model_id`, `purpose`, число токенов если известно |
| `model.failed` | ERROR | `model_id`, `kind`, `message`, номер попытки |
| `tool.invoked` | INFO | `tool`, `risk_level`, безопасные аргументы |
| `tool.denied` | WARNING | `tool`, `risk_level`, номер правила политики |
| `tool.confirmation_required` | WARNING | `confirmation_id`, `tool`, безопасные аргументы |
| `tool.failed` | ERROR | `tool`, `kind` (`arguments` — не по схеме, `handler` — ошибка обработчика), `message` |
| `evaluation.started` | INFO | номер попытки |
| `evaluation.revision_requested` | INFO | замечания, оставшиеся правки |
| `evaluation.completed` | INFO | вердикт, проверки |
| `task.finished` | INFO | статус, число шагов, число правок; при `failed` — короткая причина |
| `thread.message_received` | INFO | `thread_id`, текст сообщения клиента |
| `thread.task_dispatched` | INFO | `thread_id`, `run_id`, `goal`, `payload` задачи |
| `thread.replied` | INFO | `thread_id`, `run_id` или пусто, `kind` ответа, текст ответа |

Новое имя сначала появляется в этой таблице, потом в коде. Синонимы не заводятся.

### 13.3. Шина и подписчики

Первая шина — внутрипроцессная, синхронная. Публикатор не знает подписчиков, не импортирует логгер и HTTP. Тот же конверт позже пересылается во внешний брокер без правки публикаторов.

Подписчики:

- stdout — JSON-строка на событие;
- счётчики — прогоны по статусу, выборы ролей, исходы инструментов, маршруты, вердикты;
- лента — хранит события прогона по `run_id`, отдаёт API и панели;
- лента треда — хранит события с пустым `run_id` по `correlation_id`; так видны разбор сообщения и маршрут модели приёмной;
- брокер — дописывает тот же конверт во внешний журнал. Чтение восстанавливает порядок по `run_id` и `seq`. Публикаторы не меняются.

Отключение любого подписчика не меняет решений роутера, политики и оценщика.

### 13.4. Уровни и редакция

INFO — переходы, выбор роли, маршрут, инструмент с безопасными аргументами, вердикт. DEBUG — сырой промпт и тела внешних документов; вне локальной среды выключен. WARNING — `confirm` и `deny`. ERROR — `model.failed` и `tool.failed`. Внутренняя ошибка runtime отражается в `task.finished` со статусом `failed`.

В журнал на любом уровне не попадают пароли, ключи моделей, заголовок `Authorization`. Редакция выполняется до публикации.

## 14. Безопасность

- Секреты только из окружения. Не в репозитории, каталоге, скилле, событии, памяти, ответе API.
- Ядро стартует на моках без единого секрета внешней системы. Секрет нужен лишь включённому адаптеру; его отсутствие — отказ старта с указанием переменной.
- Потолок риска: платформа задаёт, роль сужает. Модель, скилл и payload не поднимают.
- `destructive` закрыт до отдельного платформенного решения.
- Подтверждение привязано к `run_id` и `args_hash`, одноразовое, с истечением.
- Роль не читает чужой `run` и не вызывает инструмент вне своих скиллов.
- Ошибка политики — `deny`, не исключение.

## 15. HTTP-край

Пакет `api` — единственный HTTP-вход. Роут проверяет вход, вызывает сервис приложения, возвращает схему. Сервис вызывает оркестратор и ленту; правил риска, выбора модели и оценки не содержит.

Ресурсы контракта:

| Операция | Смысл | Результат |
| --- | --- | --- |
| Создать задачу | Принять задачу, запустить прогон | `run_id`, `correlation_id` |
| Прочитать прогон | Состояние сотрудника, статус, ожидающее подтверждение если есть | Поля прогона |
| Прочитать ленту | События прогона с `seq` | Список конвертов |
| Ответить на подтверждение | `approve` или `reject` на `confirmation_id` | Новое состояние прогона |
| Открыть тред | Создать пустой диалог | `thread_id` |
| Прочитать тред | Сообщения, связанные прогоны, ожидающее подтверждение | Поля треда |
| Написать в тред | Принять сообщение клиента, провести его через приёмную, вернуть ответ | Поля треда |
| Ответить в треде на подтверждение | `approve` или `reject` на `confirmation_id` ожидающего прогона треда | Поля треда |
| Прочитать ленту треда | События треда с пустым `run_id` | Список конвертов |
| Список тредов | Сводки тредов из хранилища, новые сверху | Список сводок |
| Состояние платформы | Адаптеры без секретов, включённые роли с `description` и текущим состоянием сотрудника, число записей каталога | Поля состояния |

Ресурсы прогона остаются: панель читает по ним подробности каждого прогона треда.

Состояние платформы читается без модели и инструментов и не меняет ничего. Секреты, адреса ящиков и имена моделей провайдера в него не входят.

Различимые результаты, не ошибка сервера: `no_role`, `WaitingConfirmation`, `NoModelError`, ошибка валидации ограничений. Схемы наружу — поля конверта и прогона; типов SDK нет.

Эндпоинтов, существующих только для одной роли, в `api` нет. Доменный ресурс принадлежит плагину роли, если нужен вообще.

Корень сборки внедряет порты. Роут адаптер не создаёт и окружение не читает.

## 16. Корень сборки и конфигурация

Один корень сборки собирает: список включённых ролей, каталог моделей, адаптеры провайдеров, backend памяти, хранилище тредов, оценщика, подписчиков шины, пределы из раздела 5, приёмную с глубиной истории треда `dialog_history_limit` (дефолт 12 сообщений).

Оркестратор одного процесса исполняет задачи последовательно: `submit` и `confirm` защищены одной блокировкой, второй запрос ждёт завершения первого. Так два параллельных HTTP-запроса не ведут один автомат одновременно. Параллельные сотрудники — вопрос нескольких процессов, не этого этапа.

Конфигурация — переменные окружения по 12-factor. Файл `.env` только для локальной разработки и в репозиторий не входит. Включённый адаптер без нужной переменной — отказ старта. Выбор адаптера: `mock`, `local`, `cloud`. Память: `memory`, `sqlite`, `shared`. Живой каталог и путь брокера включаются отдельно и по умолчанию выключены.

Тесты ядра собирают корень на моках: `MockLlmProvider`, `MockMemory`, моковые инструменты, mock-оценщик, синхронная шина. Сеть не открывается.

## 17. Инструментарий репозитория

Python 3.12+, FastAPI, pytest, mypy в строгом режиме, ruff для линтинга и форматирования, pre-commit. Коммиты — Conventional Commits. Тесты разделены на unit (чистые решения: политика, роутер, оценщик, автомат) и integration (прогон на моках через оркестратор). Фронтенд — React, этап 3.

Каркас Django, DRF и Celery в репозитории не используются.

## 18. Как менять контракт

В одной задаче с поведением правятся: этот документ, при смене критерия — `docs/roadmap.md`, при смене метода — соответствующий файл `.cursor/skills/ai-department-development/`.

Изменения требуют правки документа: новое состояние, статус, событие, поле конверта, раздел памяти, уровень риска, поле требований к модели, публичный порт, правило политики, предел конфигурации.

Не требуют: внутренняя правка адаптера без смены сигнатуры, новый плагин роли, новая запись каталога.

Проверка перед слиянием: имена событий и состояний в коде совпадают с таблицами разделов 6, 7, 13; по этому документу можно добавить роль, не читая почтовый плагин.

## 19. Приёмная и треды

### 19.1. Тред

Тред — диалог клиента с платформой. Поля: `thread_id`, упорядоченный список сообщений, список `run_id` связанных прогонов, ожидающее подтверждение, если есть.

Сообщение: `author` из `{user, assistant}`, `text`, необязательный `run_id`, для ответов — `kind` из `{answer, completed, waiting_confirmation, no_role, rejected, failed}`.

Прогон, созданный из треда, получает `correlation_id = thread_id`. Так лента прогона и лента треда связаны одной меткой.

Треды хранятся через порт `ThreadStore`: `save(thread)`, `load(thread_id) -> thread | None`, `list() -> list[summary]`. Сводка треда: `thread_id`, `created_at`, `updated_at`, число сообщений, текст последнего сообщения не длиннее 120 символов. Адаптеры: в памяти процесса и SQLite; выбор — конфигурацией `threads_backend` (`memory` по умолчанию, `sqlite` с путём `threads_sqlite_path`). Приёмная после каждого изменения треда сохраняет его целиком и читает из хранилища при обращении.

Прогоны тред не переживают перезапуск вместе с тредом: после старта ожидающий прогон, которого оркестратор не знает, считается потерянным — приёмная снимает ожидание и добавляет в тред ответ `kind = failed` с текстом о перезапуске при первом обращении к треду. Подробности прогона по `run_id` после перезапуска недоступны; сообщения треда остаются.

### 19.2. Разбор сообщения

Приёмная принимает текст клиента и последние `dialog_history_limit` сообщений треда. Она один раз обращается к роутеру с требованиями шага: `capabilities = {reasoning, tools}`, `preferences = (cheap, fast)`, `purpose = intake`; запрос идёт с `temperature = 0`. Имя модели ей неизвестно. Маршрут и вызов публикуются как `model.routed` и `model.called` с пустым `run_id`.

Модель получает список включённых ролей: `role_id` и `description` каждой. Инструменты ролей, схемы и потолки риска ей не передаются. Она возвращает одно из двух решений:

- `reply` — текст ответа клиенту без создания прогона: приветствие, вопрос о возможностях, сообщение не по делу, задача, под которую нет роли.
- `dispatch` — `role_id` из списка, `goal` для сотрудника.

Решение модель выражает структурированным вызовом одного из двух вариантов — `dispatch` или `reply` — в формате tool-call провайдера. Это варианты ответа приёмной, а не инструменты реестра: у них нет обработчика и уровня риска, через шлюз они не идут и ничего не исполняют. Если модель вернула текст вместо вызова, текст читается как JSON того же вида.

Если ответ модели не разбирается ни как вызов, ни как JSON, ни как связный текст — обрывок вызова, пустой объект, — приёмная повторяет тот же запрос один раз; второй такой ответ даёт `reply` с просьбой сформулировать задачу. Оба вызова публикуются как `model.called`.

`role_id` вне списка при единственной включённой роли заменяется на неё; при нескольких ролях остаётся как есть, и оркестратор даёт `no_role`. Вырожденный `goal` — пустой, шаблонный или скопированный из подсказки — заменяется дословным текстом сообщения клиента. Обычный текст вместо решения считается `reply` с этим текстом. JSON-объект, который не является допустимым решением, даёт `reply` с просьбой уточнить задачу: сырой JSON клиенту не показывается. `NoModelError` и `ProviderError` дают ответ `kind = failed` без прогона.

При `dispatch` приёмная подставляет `payload.channel = role_id` и `payload.request` — исходный текст сообщения клиента, если модель их не задала, и вызывает оркестратор как любой клиент. Так сотрудник видит дословную просьбу, а не только пересказ модели приёмной. Приёмная вызывает оркестратор: с `goal`, платформенными ограничениями по умолчанию и `correlation_id = thread_id`. Выбор роли по-прежнему делает оркестратор по `score`; решение модели — только подсказка через payload. Роль, которая хочет получать задачи из диалога, отвечает на `payload.channel == role_id` оценкой не ниже порога.

Приёмная не вызывает инструменты, не завершает прогон, не меняет состояние сотрудника и не трогает память разделов `run` и `agent`.

### 19.3. Ответ

Ответ клиенту строится детерминированно из снимка прогона, без второго вызова модели:

| Снимок | `kind` | Текст |
| --- | --- | --- |
| статус `no_role` | `no_role` | Ни один сотрудник не взял задачу; если `failure_reason = busy` — подходящий сотрудник занят другим прогоном, попросить повторить позже |
| состояние `WaitingConfirmation` | `waiting_confirmation` | Роль, инструмент, безопасные аргументы и вопрос «разрешить или отклонить» |
| статус `completed` | `completed` | `output.summary`, если оно строка; иначе короткое сообщение о завершении |
| статус `rejected` | `rejected` | Сообщение о непройденной оценке и `output.summary`, если есть |
| статус `failed` | `failed` | Короткая причина из `failure_reason` |

Пока тред ждёт подтверждения, новое сообщение клиента не разбирается моделью и не создаёт прогон: приёмная повторяет вопрос о подтверждении. Так сотрудник не получает вторую задачу, пока первая стоит в `WaitingConfirmation`.

Ответ на подтверждение в треде передаётся оркестратору как обычное `approve` или `reject` по `run_id` ожидающего прогона. Приёмная не выполняет инструмент и не обходит `WaitingConfirmation`. Итоговый снимок снова превращается в ответ по таблице выше.

События: `thread.message_received` на входе, `thread.task_dispatched` после создания прогона, `thread.replied` на каждый ответ.
