# План разработки AI Department

Этапы и критерии приёмки. Контракты — в `docs/architecture.md`. Этап считается закрытым, когда все его критерии выполнены и проверены; следующий этап до этого не начинается.

Общий принцип: сначала порты и моки, потом одна реализация каждого порта, потом вторая. Набор провайдеров, брокер и панель заранее не создаются.

## Этап 0. Спецификация

Состав:

- `docs/architecture.md`, `docs/roadmap.md`;
- методология в `.cursor/skills/ai-department-development/` и правила `.cursor/rules/`.

Критерии приёмки:

- В репозитории нет кода приложения, зависимостей и каркаса.
- Все имена состояний, статусов, событий, уровней риска и разделов памяти определены в `architecture.md`.
- Pack в `.cursor/` не противоречит `docs/`.
- По спеке можно описать плагин новой роли, не зная о почте.

Не входит: любой код, выбор конкретной локальной модели, схема данных SQLite.

## Этап 1. Ядро на моках и демонстрационная роль

Этап разбит на три шага, принимаемых по очереди.

### 1a. Ядро

Состав:

- `domain`: типы задачи, прогона, состояний, статусов, уровней риска, требований к модели, конверта.
- `events`: синхронная внутрипроцессная шина, конверт с `seq`.
- `llm`: каталог из конфигурации, роутер, порт `LlmProvider`, `MockLlmProvider`.
- `tools`: реестр, шлюз, политика, записи подтверждений, моковые инструменты.
- `memory`: порт, `MockMemory`, `InMemory`.
- `evaluation`: порт, детерминированный оценщик, mock-оценщик, цикл правок.
- `runtime` и `orchestrator`: общий автомат, реестр ролей, выбор роли, привязка скиллов, выдача результата после оценки.
- Тестовая роль без домена в `roles/<role_id>/` для тестов ядра.
- `observability`: подписчики stdout, счётчики, лента.
- Корень сборки на моках. Инструментарий репозитория: pytest, mypy, ruff, pre-commit.

Критерии приёмки — тесты на моках без сети:

- Выбор роли по `score`; ниже порога — статус `no_role`, модель не вызывалась.
- Все переходы автомата из раздела 6 `architecture.md`; `Completed` только из `Evaluating`; сотрудник в `Idle` после `Completed` и `Failed`.
- `confirm` для `act`, `allow` после подтверждения, повтор требует нового подтверждения; подтверждение из другого прогона или с другими аргументами не принимается.
- `deny` для инструмента выше потолка роли, для `destructive`, для инструмента вне скиллов роли.
- Два шага с разными требованиями получают разные модели; выключенная модель не выбирается; пустой список — `NoModelError` и статус `failed`.
- Правка evaluation возвращает в `Running`; исчерпание лимита даёт статус `rejected`, не `completed`.
- Два прогона одной роли не читают `run` друг друга; `agent` виден следующему прогону той же роли.
- Один `run_id` собирает ленту; `seq` строго возрастает; `evaluation.completed` раньше `task.finished` в успешном прогоне.
- Секрет из окружения не появляется в событиях уровня INFO.
- В `runtime`, `orchestrator`, `evaluation`, `memory`, `tools`, `llm` нет импортов из плагинов ролей и слов «mail», «imap», «smtp».
- mypy и ruff чистые.

Не входит: живой провайдер, живая внешняя система, SQLite, HTTP, панель.

### 1b. Первые реальные адаптеры и тонкий API

Состав:

- Адаптер `LlmProvider` к OpenAI-совместимому локальному endpoint. Включается конфигурацией; ключ и URL из окружения.
- `MemoryBackend` на SQLite. Включается конфигурацией.
- `api`: создать задачу, прочитать прогон, прочитать ленту, ответить на подтверждение. Корень сборки для процесса.

Критерии приёмки:

- Тесты ядра из 1a проходят без изменений с переключением адаптеров на моки.
- Тест API поднимает приложение на моках и проверяет четыре операции, включая `no_role`, `WaitingConfirmation` и `NoModelError` как различимые ответы.
- Отсутствие переменной окружения у включённого адаптера — отказ старта с указанием переменной.
- Замена `InMemory` на SQLite не меняет код тестовой роли.
- По коду `api` нельзя понять, какая роль демонстрационная.

Не входит: облачный провайдер, брокер, панель, аутентификация API сверх локального запуска.

### 1c. Демонстрационная роль: почта

Состав — отдельный пакет плагина:

- `score` по payload, скиллы, потолок риска `act`, `output_schema`.
- Инструменты: чтение ящика — `read`, подготовка черновика — `draft`, отправка — `act`. Удаление, если оно есть, — `destructive` и закрыто.
- Обработчики читают учётные данные из окружения.
- Регистрация в реестре через корень сборки.

Критерии приёмки:

- Роль подключена последней: ядро 1a и 1b не менялось.
- Прогон роли на моковом провайдере и моковых обработчиках почты проходит тот же автомат и те же события.
- Отправка письма без подтверждения невозможна: тест доказывает `confirm`.
- Ручная проверка с живым ящиком и локальной моделью: чтение и черновик, без отправки. Результат проверки фиксируется в ленте, не в коде.

Не входит: отправка писем в ручной проверке, второй почтовый протокол, интерфейс входящих.

## Этап 2. Вторая роль

Состав:

- Вторая роль — `records`, учёт записей, не почта. Отдельный плагин `roles/records/`.
- Инструменты: `list_records` — `read`, `write_record` — `draft`. Потолок роли `draft`. Хранилище записей живёт в плагине, секретов нет.
- Оценка задачи. `records`: `0.75`, если `payload.channel` равен `records` или список `payload.channels` содержит `records`, иначе `0`. Почта по-прежнему `0.92` при `payload.channel` равном `mail` и дополнительно `0.5`, если `payload.channels` содержит `mail`.
- Новая запись каталога не требуется: шаг заявляет требования, модель по-прежнему выбирает роутер.

Критерии приёмки:

- Роль проходит полный прогон на моках без правки `orchestrator`, `runtime`, `evaluation`, `memory`, `tools`, `llm`, `events`.
- Смена модели первой роли — правка конфигурации каталога, не кода.
- Задача, подходящая обеим ролям, уходит к роли с большим `score`; задача ниже порога обеих — `no_role`.
- Скилл одной роли недоступен другой: тест доказывает `deny`.
- Разделы `agent` двух ролей изолированы.

Если для второй роли пришлось менять ядро — этап не принят, сначала правится контракт в `architecture.md`.

Не входит: панель, облачный провайдер, брокер.

## Этап 3. Панель

Состав:

- React-приложение, читающее ленту и прогон через `api`.
- Экраны: состояние сотрудника, маршрут модели с отклонёнными кандидатами, решение инструмента, шаги evaluation, кнопка ответа на подтверждение.
- Представления ролей для доменных полей payload, если роль их предоставляет.

Критерии приёмки:

- Панель показывает прогон на моках без живых внешних систем.
- Кнопка подтверждения отправляет `approve` или `reject` в `api`; инструмент из панели не вызывается.
- Смена роли не требует новой оболочки, только данных ленты.
- Ядро и `api` не переписаны; если панели не хватило поля, оно сначала добавлено в конверт в `architecture.md` и шине.
- В состоянии браузера нет источника истины для потолка риска, `max_revisions` и каталога.

Не входит: второй журнал для UI, экран «входящие» как каркас продукта, брокер.

## Этап 4. Другие реализации портов

Состав, каждый пункт — отдельная задача:

- Облачный `LlmProvider`: новый адаптер и строки каталога.
- Распределённый `MemoryBackend`.
- Пересылка конверта во внешний брокер; подписчики читают из него, восстанавливая порядок по `run_id` и `seq`.
- Живой источник `ModelCatalog.list()`.

Критерии приёмки:

- Публичные контракты портов этапов 1–3 не изменились.
- Тесты ядра на моках проходят без правок.
- Код ролей не изменился.
- Через брокер `evaluation.completed` по-прежнему предшествует `task.finished` по `seq`.

Не входит: открытие `destructive`.

## Этап 5. Приёмная: одно окно

Состав:

- Пакет `dialog`: тред, приёмная, детерминированный ответ по снимку прогона. Контракт — раздел 19 `architecture.md`.
- Поле `description` в контракте роли; роли `mail`, `records` и тестовая роль отвечают на `payload.channel == role_id`.
- События `thread.message_received`, `thread.task_dispatched`, `thread.replied`; лента треда.
- Пять ресурсов треда в `api` поверх прежних четырёх ресурсов прогона.
- Панель становится одним окном: лента сообщений, поле ввода, кнопки подтверждения внутри ответа, подробности прогона по требованию.

Критерии приёмки — тесты на моках без сети:

- Сообщение, которое модель приёмной разобрала как `reply`, не создаёт прогон; `thread.replied` с `kind = answer`.
- Сообщение, разобранное как `dispatch`, создаёт прогон с `correlation_id = thread_id`, `payload.channel = role_id` и `payload.request` = исходный текст; ответ треда равен `output.summary` завершённого прогона.
- Прогон в `WaitingConfirmation` даёт ответ `kind = waiting_confirmation`; `approve` через тред завершает прогон и даёт ответ `kind = completed`; инструмент выполняется только после `approve`.
- Пока тред ждёт подтверждения, новое сообщение не вызывает модель и не создаёт прогон.
- `NoModelError` на шаге приёмной — ответ `kind = failed`, прогона нет.
- Ответ модели обычным текстом становится `reply`; JSON без допустимого решения — `reply` с просьбой уточнить, без сырого JSON.
- `orchestrator`, `runtime`, `evaluation`, `memory`, `tools`, `llm`, `events` не изменены ради приёмной; `dialog` не упоминает домен ролей.
- Панель ведёт диалог на моках; кнопка подтверждения шлёт решение в API треда и не вызывает инструмент.

Не входит: сохранение тредов между запусками, несколько параллельных прогонов в одном треде, разбор подтверждения из свободного текста.

## Этап 6. Живой прогон на слабой модели

Причина: прогон почтовой роли на локальной модели через живой ящик показал сбои, которые моки не ловили: приёмная отвечала сама вместо передачи задачи, подтверждение запрашивалось на заглушку вместо адреса, итог «письмо отправлено» без единого вызова инструмента проходил оценку.

Состав:

- Приёмная: решение структурированным вызовом `dispatch`/`reply`, `temperature = 0`, один повтор неразборного ответа, замена `role_id` вне списка при единственной роли, замена вырожденного `goal` текстом клиента. Раздел 19.2.
- Порт провайдера: необязательная `temperature`. Раздел 9.4.
- Шлюз: проверка аргументов по схеме инструмента до политики; `tool.failed` с `kind = arguments`. Раздел 10.1.
- Оценка: проверка `tool_evidence`; трасса несёт `bound_tools` и попытки вызова с `invoked = false`. Раздел 11.
- Почтовая роль: адрес ящика в инструкции и схемах, формат адреса и id письма в схемах, `Date` и `Message-ID` у исходящих, терпимый `limit`.

Критерии приёмки — тесты на моках без сети:

- Ответ приёмной вызовом `dispatch` предпочтительнее текста; обрывок вызова не уходит клиенту и повторяется один раз.
- Вызов с аргументами не по схеме даёт `tool.failed` с `kind = arguments`, подтверждение не открывается, обработчик не вызван; следующий корректный вызов проходит обычный путь.
- Итог без единого обращения к инструментам у роли с инструментами уходит на правку с замечанием `tool_evidence`; отклонённый человеком `act` считается обращением, и прогон завершается `completed` без правок.
- `LlmRequest` с `temperature` вне `0..2` отвергается; адаптер передаёт поле только когда оно задано.
- Схемы почтовой роли отвергают заглушки вида `[адрес получателя]` и `<id из списка>`.

Не входит: оценщик качества на модели, подбор модели приёмной под долю верных решений, автоматическая подстановка адреса ящика вместо заглушки.

## Этап 7. Рабочий департамент

Причина: платформа проходит прогон, но не годится для ежедневной работы. Перезагрузка страницы открывает новый пустой диалог, тредов нет после перезапуска процесса, нет списка диалогов и состояния сотрудников, запуск только из виртуального окружения вручную, два параллельных запроса ведут один автомат одновременно.

Состав:

- Порт `ThreadStore` с адаптерами в памяти и SQLite; приёмная читает и сохраняет треды через него. Потерянный после перезапуска прогон снимается с ожидания с ответом `kind = failed`. Раздел 19.1.
- Ресурсы `GET /threads` и `GET /health`. Раздел 15.
- Конфигурация `THREADS_BACKEND`, `THREADS_SQLITE_PATH`. Раздел 16.
- Оркестратор: одна блокировка на `submit` и `confirm`; `no_role` с `failure_reason = busy`, когда подходящий сотрудник занят. Разделы 7, 16, 19.3.
- Панель: список диалогов, новый диалог, текущий диалог помнится в браузере и восстанавливается после перезагрузки, состояние сотрудников в шапке.
- Почтовая роль: `list_unread` забирает ограниченный фрагмент письма, а не письмо целиком; по-прежнему только новейшие `limit` писем.
- Запуск: `Dockerfile`, `.dockerignore`, `Makefile` с целями установки, проверки, тестов, сборки панели и запуска.

Критерии приёмки — тесты на моках без сети, кроме отмеченного:

- Тред, сохранённый в SQLite, читается новым экземпляром приёмной с теми же сообщениями; его ожидающий прогон после «перезапуска» снят, в треде последнее сообщение `kind = failed`.
- `GET /threads` отдаёт сводки новых тредов сверху с числом сообщений и текстом последнего.
- `GET /health` отвечает без вызова модели и инструментов, в ответе нет значений секретов и имён моделей провайдера.
- Два одновременных `submit` из разных потоков не ломают автомат: один прогон завершается, второй идёт следом или получает `no_role` с `failure_reason = busy`.
- Задача роли, сотрудник которой в `WaitingConfirmation`, получает `no_role` с `failure_reason = busy`, и ответ треда говорит о занятости.
- `list_unread` на усечённом RFC822 даёт корректные `from`, `subject`, `date`, `snippet`.
- Панель собирается `npm run build`; ручная проверка в браузере: перезагрузка страницы сохраняет диалог, новый диалог появляется в списке, подтверждение из списка тредов работает.
- `docker build` собирает образ с панелью; `make check` прогоняет ruff, mypy и pytest.

Не входит: несколько процессов и параллельные сотрудники одной роли, аутентификация панели, оценщик качества на модели.

## Вне плана

Открытие уровня `destructive` — отдельное платформенное решение с собственной спекой, правкой политики и тестами. Ни один этап выше его не включает и не подразумевает.

## Дисциплина этапов

- Пока критерии текущего этапа не закрыты, не начинаются панель, облачные провайдеры и брокер.
- Критерий этапа меняется правкой этого документа в той же задаче, что и причина смены.
- Тест, который нужно ослабить ради сценария одной роли, указывает на ошибку контракта, а не на лишний тест.
